# 固定双板 UDP：2026-10-05 上板验证

这是新的轻量固定 IP/MAC UDP 的独立硬件验证工程，不是正式双板多媒体播放器。它不读 TF 卡、不使用 SDRAM、不输出 HDMI 图片或声音，不需要电脑串口，也不能用 Ping 验证。原单板工程、回退 bit、旧 Ethernet smoke/IMGF 测试工程不覆盖。

## 配套下载文件

- A 接收与校验板：`prj/board_a/FIXED_UDP_HW_A_20261005.bit`
- B 发送板：`prj/board_b/FIXED_UDP_HW_B_20261005.bit`

只使用以上一对新文件，不能和旧 smoke、IMGF 或正式播放器混配。给两块板贴 A/B 标签。建议每次只连接目标板的一根 USB 下载线，在 BitWriter 选择 `PROGRAM_SRAM`，分别给 A/B 下载对应文件；先不固化到 Flash。**两板下载后必须持续供电**：SRAM 下载断电失效，断电后需要重新下载。如果 USB 下载线同时是唯一供电线，不能拔线后还期待程序保留；应先按板卡手册使用支持的独立供电方式，再采用只连接一个下载器的办法。网络可以先接好，也可以两板下载完成后再接。

## 操作步骤

1. 两板分别供电，用网线直连**之前已经通过 Ethernet smoke 的同一对网口**。程序使用 `phy1_rgmii_*`，另一网口不参与本测试。
2. 等待约 2 秒、确认网口 Link 指示正常，两块板的 K1 复位键分别按一下并松开。两板第一个用户 LED 应有心跳闪动；此时不按发送键，不应已经完成传帧。
3. **按住 B 板 K2 约 3 秒，然后松开**。K2 对应 FPGA B2 引脚；K1/A2 是复位，不是发送。按住会连续发送，松开后当前帧仍会传完。
4. 检查下表结果。两板共同复位清除结果，重复上述测试 3 次。先不要用只复位一块板来判断本诊断是否通过：它没有正式播放器的 LNK1 世代恢复模块。

下文 LED1～4 对应程序 `led[0]`～`led[3]`、引脚 A4/A3/C10/B12，**不是 RJ45 自带的 Link/Activity 灯**。表中“置位”指程序输出为 1；常见正常现象为亮，若板上 LED 极性不同应以复位前后的变化为准，LED1 的心跳最易定位。

| 用户 LED | A 板含义 | B 板含义 |
| --- | --- | --- |
| LED1 | 心跳，约每 0.5 秒翻转 | 心跳，约每 0.5 秒翻转 |
| LED2 | 已接收到通过应用校验的 IMG4 包 | 已发出至少一个 IMG4 包 |
| LED3 | 完整 640×480 帧的像素和图层标签全部检查正确 | 最后一包的确认已收到，整帧发送成功 |
| LED4 | 错包、像素/标签/分辨率/帧长度异常，锁存报警 | 已收到 A 返回的有效 UDP 确认包，**这是成功标志，不是报警** |

通过标准：A 的 LED2、LED3 置位，LED4 不置位；B 的 LED2、LED3、LED4 置位；两板 LED1 继续闪动。B 只有 LED2 改变，不能证明通信成功。

如果不通过，请反馈按 K2 前后 A/B 的四个用户 LED 状态、网口 Link 灯是否亮、使用哪个网口，最好附照片：

- 没有心跳：先核对所下载文件、供电和是否仍按住复位。
- B LED2 置位、A LED2 不变：核对配套文件、网口和网线，检查 B→A 接收。
- A LED2 置位，但 B LED4 不变：优先检查 A→B 的确认返回；不要以 B 发包灯作为通过依据。
- A LED4 置位：需要排查实际接收的数据/帧校验，不把错误当成通信成功。
- B LED4 置位但两板 LED3 不变：返回路径已收到过确认，但整帧尚未完成，需要进一步定位丢包/重传。

## 验证的内容与边界

真实板间走标准 Ethernet/IPv4/UDP。B 从逻辑生成确定性的测试图，不占整帧缓存；每帧 307200 个 RGB+图层标签像素，分 1200 个 IMG4 包（每包 UDP 载荷 1042 字节）。A 用现有 `image_packet_rx` 校验、排重并逐像素检查，真实返回 12 字节 IAK2 UDP 确认。B 只有收到匹配 token/序号的最后一个确认才置位“完成”。确认超时 100ms 重传；没有确认不会假装完成。

固定地址：A `192.168.10.11 / 02:00:00:00:00:0b`；B `192.168.10.12 / 02:00:00:00:00:0c`；UDP 双向端口 `20482`。不做 ARP/ICMP/Ping，不需配置电脑 IP。使用原 MAC、client FIFO、PLL 和 RGMII 接线，没有修改这些 IP 的内部实现。

诊断专用源 `fixed_udp_hw_pattern.v` 不等于正式 TF 图片发送器；它避免增加 256 像素缓存，并能在重传时重新计算测试像素。A 诊断顶层在 UDP 应用数据/描述符之后增加同拍寄存，并把像素检查分一拍处理，以降低 125MHz 路径长度。这些局部流水修改没有直接套到正式播放器。这里的成功不证明 TF/FAT、SDRAM、HDMI、音频、四图切换、串口、歌词或正式播放器最终时序已通过。

以上在继承 smoke 时钟和 TEMAC IP 约束下测得，没有放宽频率或删除违例来取得正裕量。外部 RGMII 输入/输出延迟、完整 IO/CDC 约束仍未做完整审计，裕量较小，不能称为完全硬件时序保证，真实线缆上板验证仍必要。

`sim/modelsim_hw.log`：真实诊断 A/B 顶层完成两帧测试；第一次故意丢一个返回确认，成功重传且没有重复发布像素；复位、K2 发送和 LED 语义检查通过。Errors=0、Warnings=0。这里用 test-only 传输桥和真实 fixed-peer 端点，没有仿真加密 TEMAC、RGMII/PHY 电气层或实际线缆。波形 `sim/fixed_udp_hw_full.wlf`。

`sim/check_ipv4_sum.js` 穷举全部 1048576 个 20-bit 校验和，证明新的 RX 校验和判等逻辑与原折叠结果相同。正式播放器另外完成 40 项回归（108 个既有测试/FIFO 警告），gate 综合 A=13453 LUT（68.64%）、B=10932（55.78%）；不要把这两个综合数字和上面的诊断布局数字混为一谈。

检查并冻结最终文件：`node ./dual_board/fixed_udp_hw/sim/snapshot_hw_validation.js`，输出 `validation_20261005.json`，记录 bit、源码、报告哈希和未上板边界。
